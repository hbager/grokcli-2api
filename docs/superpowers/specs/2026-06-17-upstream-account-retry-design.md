# 上游錯誤自動換號重試設計

日期：2026-06-17
狀態：已核准

## 目標

當 LLM 上游請求失敗時，自動改用另一個可用帳號重試。管理員可在系統設定中指定額外重試次數 `N`；包含首次請求在內，同一個用戶請求最多嘗試 `N+1` 個不同帳號。只有所有允許的嘗試都失敗後，才向客戶端回報上游問題。

此行為必須同時套用於 Go 正式執行路徑及 Python 相容路徑，並覆蓋以下 API：

- `/v1/chat/completions`
- `/v1/messages`
- `/v1/responses`

## 非目標

- 不重試本服務在呼叫 LLM 上游前發現的客戶端錯誤，例如無效 API Key、無效 JSON、缺少必要欄位。
- 不在串流已輸出有效模型內容後拼接另一個帳號的回答。
- 不因單次 `400` 或 `404` 直接永久停用帳號；帳號狀態仍由既有冷卻、模型封禁及停用政策管理。
- 不在同一請求中重複使用已失敗的帳號。

## 設定模型

新增持久化設定：

```json
{
  "upstream_retry_count": 3
}
```

設定語義如下：

- `upstream_retry_count` 表示首次請求失敗後，最多額外換號重試幾次。
- 預設值為 `3`。
- 合法範圍為 `0–63`。
- `0` 表示只執行首次請求，不重試。
- 總嘗試上限為 `upstream_retry_count + 1`。
- 可用帳號少於總嘗試上限時，只嘗試所有不同的可用帳號，不重複帳號。

系統設定頁將欄位顯示為「上游報錯自動換號重試次數」，並說明：「設為 3 時，最多嘗試 4 個不同帳號」。

### 舊設定相容

現有 `max_failover_attempts` 代表總嘗試帳號數，與新設定語義不同。相容規則如下：

1. 若存在 `upstream_retry_count`，一律以它為準。
2. 若不存在新設定但存在舊設定，使用 `max(0, max_failover_attempts - 1)` 作為有效重試次數。
3. 若兩者都不存在，使用預設值 `3`。
4. 管理頁只寫入新設定，不再寫入舊設定。
5. 舊資料 `max_failover_attempts=4` 升級後仍等價於最多嘗試四個帳號。

Go 每個新請求都讀取持久化設定的有效值，使管理頁修改無須重啟即可生效。Python 使用相同設定及相同換算規則。

## 重試範圍

只有已送往 LLM 上游的請求錯誤才進入換號重試。

### 必須重試

在尚未向客戶端輸出有效模型內容時，下列情況都必須換號：

1. 上游回傳任何非 `2xx` HTTP 狀態，包括所有 `4xx`、`5xx` 及其他非成功狀態。
2. DNS、TCP、TLS、代理或其他連線錯誤。
3. 連線或讀取逾時。
4. 上游在完成有效回應前斷線。
5. HTTP 200 回應無法解析成有效模型資料。
6. HTTP 200 回傳空 Body、HTML、閘道攔截頁、錯誤 JSON 或其他非模型回應。
7. 回應沒有任何有效模型輸出：
   - 沒有非空白 `content`；
   - 沒有非空白 `reasoning`；
   - 沒有 `tool_calls` 或相容的 function call。
8. `output_tokens=0` 或 `completion_tokens=0`，且同時不存在任何有效文字、推理或工具呼叫。

Token 統計只作為輔助訊號。即使 `output_tokens=0`，只要存在文字、推理或工具呼叫，仍視為成功，避免因上游計量錯誤重複執行請求。

### 不重試

以下情況不換號：

1. 客戶端取消請求或連線已中斷。
2. 本服務在送往上游前拒絕的輸入或鑑權錯誤。
3. 串流已向客戶端輸出有效文字、推理或工具呼叫後才失敗。

SSE keepalive、協議外殼、角色欄位及沒有模型內容的控制事件不算有效輸出；只輸出這些事件後仍可安全換號。

## 請求流程

```text
讀取 upstream_retry_count = N
             │
             v
選出最多 N+1 個不同的可用帳號
             │
             v
使用第一個帳號呼叫 LLM 上游
             │
      ┌──────┴──────┐
      │             │
    成功      上游錯誤或空回覆
      │             │
      v             v
 回傳結果    尚有帳號且未輸出有效內容？
                    │
             ┌──────┴──────┐
             │             │
            是             否
             │             │
             v             v
       換下一帳號      回報上游問題
```

例如 `N=3`：

```text
帳號 A：首次請求失敗
帳號 B：第 1 次重試失敗
帳號 C：第 2 次重試失敗
帳號 D：第 3 次重試成功
→ 回傳帳號 D 的完整結果
```

## 元件設計

### 共用重試政策

Go 的代理層提供單一有效嘗試上限，供 OpenAI Chat、Anthropic Messages 與 OpenAI Responses 共用。三個協議都透過同一個 `ChatService` 建立候選鏈及判定空模型輸出，避免協議間重試行為分歧。

Python 的 `account_pool.try_acquire_sequence` 繼續負責建立不重複帳號鏈，但上限改用新設定的 `N+1`。非串流與串流代理都必須對所有上游非成功狀態繼續使用下一帳號，而不再只接受既有的狀態碼白名單。

### Go 設定讀取

Go 管理 API 的 `PublicSettings` 暴露新設定及有效值；`UpdateRuntimeSettings` 驗證並持久化 `0–63`。服務端在每個 LLM 請求建立 `ChatService` 前解析有效重試次數，再把 `N+1` 作為候選鏈上限傳入代理層。

測試或無 PostgreSQL 的內嵌模式使用預設 `N=3`，除非測試明確注入其他值。

### 上游錯誤分類

Go 上游客戶端將所有非 `2xx` 狀態回傳為 `UpstreamError`。代理層只排除客戶端取消；其他上游開啟錯誤、讀取錯誤、解析錯誤與空輸出都可觸發下一帳號。

Python 移除 `_retryable_status` 對特定狀態碼的限制，改為「所有上游非成功 HTTP 狀態可換號」。本地輸入驗證不經過此函式，因此不會把客戶端請求錯誤誤當成上游錯誤。

### 串流提交邊界

串流必須在可安全換號期間保留控制權：

- 收到第一段有效文字、推理或工具呼叫前，若上游失敗或結束為空，可關閉該回應並改用下一帳號。
- 一旦有效模型內容已寫入客戶端，該回應即視為已提交。之後的錯誤只結束目前串流，不能再換號。
- 角色事件、keepalive 或空控制事件不構成提交。

這個邊界防止客戶端收到兩個不同帳號產生的回答片段或重複工具呼叫。

## 帳號狀態與觀測

每次失敗仍沿用既有帳號池機制記錄：

- 上游狀態碼或例外摘要；
- 連續失敗次數；
- 冷卻及模型封禁資料；
- 失敗使用量事件；
- 帳號選取及換號指標。

是否冷卻、封禁或停用由既有政策決定。允許本次請求因任何上游錯誤換號，不代表所有錯誤都套用相同的永久帳號處置。

敏感 Token、帳號憑證及完整上游敏感回應不得出現在客戶端錯誤或一般日誌中。

## 最終錯誤

當所有允許帳號都失敗時：

- 非串流回傳 HTTP `503`。
- 錯誤類型為 `upstream_error`。
- 錯誤代碼為 `all_accounts_failed`。
- 訊息說明已完成自動換號重試，但上游仍無有效結果。
- 各 API 使用對應的 OpenAI、Anthropic 或 Responses 錯誤封裝。

串流在尚未提交有效內容前耗盡帳號時，以對應協議的 SSE 錯誤事件結束。已提交有效內容後的中斷使用串流中斷錯誤，不宣稱已再次換號。

如果候選帳號數小於 `N+1`，訊息不宣稱完成固定 N 次重試，只表明已嘗試所有可用帳號。

## 測試與驗收

實作採用聚焦的 RED-GREEN 測試，至少覆蓋：

1. `N=3` 時最多嘗試四個不同帳號。
2. `N=0` 時只嘗試首次帳號。
3. 可用帳號少於上限時不重複帳號。
4. 上游 `400`、`404`、`429`、`500`、`502`、`503` 都會換號。
5. 其他非 `2xx` 狀態也會換號。
6. 網路錯誤、讀取錯誤、解析錯誤、空 Body、空模型輸出都會換號。
7. `output_tokens=0` 但有文字、推理或工具呼叫時視為成功。
8. 所有帳號失敗時回傳 `503 / upstream_error / all_accounts_failed`。
9. 串流在有效輸出前可換號；有效輸出後不可換號。
10. `/v1/chat/completions`、`/v1/messages`、`/v1/responses` 行為一致。
11. 新設定的讀寫、範圍限制及免重啟生效。
12. 舊 `max_failover_attempts` 到新語義的換算正確。
13. 執行相關 Go 與 Python 回歸測試。
14. 建置管理端靜態資產。
15. 執行 `git diff --check`，並確認所有修改的文字檔維持 LF。

實機可用的完成條件是：透過本地假上游依序回傳錯誤與成功結果時，三個 API 都能依設定換用不同帳號，並只把最後成功帳號的完整回應交給客戶端；若全部失敗，則回傳統一上游錯誤。
